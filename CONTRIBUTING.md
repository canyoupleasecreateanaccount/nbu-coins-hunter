# Контриб'ютинг

Дякуємо, що хочете доєднатись! Тут — як налаштувати оточення для розробки,
запустити тести локально та які є домовленості щодо стилю коду.

## Локальне середовище

Потрібен Python 3.10+. Встановіть залежності (разом із тестовими):

```bash
pip install -r scripts/requirements-dev.txt
```

Тестам браузер не потрібен (fallback на Playwright замоканий), а от щоб
реально запустити скрипти локально (і саме потрапити у сценарій з
JS-челенджем Bunny Shield) — додатково один раз:

```bash
playwright install chromium
```

## Запуск тестів

```bash
pytest tests/ -v
```

Тести не звертаються в мережу — парсинг перевіряється на локальних
фікстурах у [`tests/fixtures/`](tests/fixtures/):

- `sample_news_page.html` — скорочена, але структурно точна копія
  сторінки новин (для `check_news.py`);
- `sample_sitemap_index.xml`, `sample_sitemap_articles.xml` — копії
  `sitemap.xml` і `sitemaparticles.xml` (для `check_sitemap.py`);
- `sample_article_page.html` — копія розмітки окремої статті, зокрема
  того нюансу, що на сторінці два `<h1>` і перший завжди порожній (для
  `check_sitemap.extract_article_title`);
- `sample_catalog_page.html`, `sample_catalog_page_paginated.html` — копії
  розмітки [`catalog.html`](https://coins.bank.gov.ua/catalog.html): одна
  без пагінації (звичайний стан — увесь каталог на одній сторінці), одна
  з посиланням "далі" (для `check_lots.find_next_page_url`).

Тести `test_http_client.py` перевіряють ретраї й паузи з підробленою
сесією та підміненим `sleep`, тож вони не ходять у мережу і не чекають
по-справжньому.

Якщо НБУ колись помітно змінить розмітку сайту (інші класи, інша
структура блоків), саме ці тести, найімовірніше, першими покажуть, що
відповідний скрипт треба оновити — а разом з тестом варто оновити й
фікстуру.

## Локальний запуск скриптів

Усі три скрипти очікують змінні середовища `TELEGRAM_BOT_TOKEN` і
`TELEGRAM_CHAT_ID` (дивіться [SETUP.md](SETUP.md), як їх отримати) —
або, якщо тестуєте розсилку кільком отримувачам, `TELEGRAM_RECIPIENTS`
замість них (формат — у [SETUP.md](SETUP.md#кілька-ботів-іабо-чатів-одразу)).
Опційно — `KEYWORDS` для фільтра заголовків (той самий фільтр
використовують `check_news.py` і `check_sitemap.py`; `check_lots.py` його
не використовує — дивіться пояснення чому в докстрінгу цього скрипта й у
README).

```bash
TELEGRAM_BOT_TOKEN=... TELEGRAM_CHAT_ID=... python scripts/check_news.py
TELEGRAM_BOT_TOKEN=... TELEGRAM_CHAT_ID=... python scripts/check_sitemap.py
TELEGRAM_BOT_TOKEN=... TELEGRAM_CHAT_ID=... python scripts/check_lots.py
```

Перший запуск кожного скрипта лише створить свій файл стану
(`state/seen_news.json`, `state/seen_sitemap.json` або
`state/seen_lots.json`) із поточним станом сайту й нічого не надішле — це
нормально, так задумано.

## Стиль коду

- Код і докстрінги — англійською; документація для людей (README, цей
  файл, SETUP.md) — українською.
- Кожна публічна функція має докстрінг, що пояснює, що вона робить і
  повертає.
- Логіка, яка звертається в мережу (`fetch_articles`, `fetch_sitemap_articles`,
  `fetch_article_title`, `send_telegram`), тримається окремо від чистих
  функцій (`parse_articles_page`, `parse_sitemap_articles`,
  `extract_article_title`, `matches_keywords`,
  `select_new_matching_articles`) — так простіше тестувати без мокання
  HTTP.
- Форматування й надсилання Telegram-повідомлень — спільне для всіх
  скриптів, у [`scripts/telegram_notify.py`](scripts/telegram_notify.py);
  нову логіку сповіщень варто додавати туди, а не дублювати в кожному
  скрипті окремо.
- **Усі** запити до сайту робіть через `http_client.SiteClient` — не
  через `requests.get()` напряму. Сайт стоїть за BunnyCDN з Bunny Shield:
  без браузерного `User-Agent` він віддає 403, а на серію швидких
  запитів без спільної сесії відповідає 429, а далі — сторінкою-челенджем.
  `SiteClient` тримає одну сесію на весь прогін (щоб зберігались cookie
  захисту), витримує паузу між запитами й робить ретраї з експоненційним
  бекофом. Створюйте один клієнт на запуск і передавайте його далі.
- `User-Agent` обирається випадково з `http_client.USER_AGENTS` один раз
  на прогін (не на кожен запит — справжній браузер не міняє його посеред
  сесії).
- Хмарні/дата-центрові IP (у т.ч. GitHub Actions) сайт іноді блокує взагалі
  без шансу пройти напряму — навіть з правильним User-Agent і сесією.
  `SiteClient` тоді сам пробує (1) безкоштовний публічний проксі з кількох
  джерел (`http_client.FREE_PROXY_LIST_URLS` + Geonode) і лише потім,
  якщо конкретно це був JS-челендж, (2) headless-браузер (Playwright).
  **Проксі з росії виключаються завжди** (`EXCLUDED_PROXY_COUNTRIES`) —
  якщо додаєте нове джерело списку проксі, переконайтесь, що виключення
  так само застосовується до нього.
- Не збільшуйте кількість запитів за прогін без потреби. Це стосується
  **прямих** запитів до сайту: 5 у `check_news.py`, 2 у `check_sitemap.py`
  (сторінки новин там довантажуються лише тоді, коли в sitemap реально
  щось нове) і зазвичай 1 у `check_lots.py` (додаткові сторінки каталогу
  довантажуються лише якщо товарів справді стає більше, ніж влазить на
  одну сторінку — на практиці це рідкість). Коли пряме з'єднання
  заблоковане (зараз це майже завжди так для GitHub Actions — див. пункт
  вище), кожен такий запит додатково коштує пошуку проксі (десятки
  паралельних тестових з'єднань до кандидатів, не до самого сайту) — це
  вже свідомий, необхідний компроміс, а не те, що варто "оптимізувати".
- Уникайте зайвих коментарів у коді: якщо код можна зробити зрозумілим
  гарними назвами змінних/функцій — краще так, ніж коментар, що дублює
  очевидне.

## Перед тим, як відкривати Pull Request

1. Переконайтесь, що `pytest tests/ -v` проходить локально.
2. Якщо міняли розмітку парсингу — оновіть відповідну фікстуру в
   `tests/fixtures/` і додайте/поправте тест, що це покриває.
3. Опишіть у PR, **чому** зроблена зміна, а не лише що саме змінилось —
   це допомагає при рев'ю.

CI (`.github/workflows/tests.yml`) автоматично прожене тести на кожен push
і pull request у `main`.
