# Налаштування

Інструкція для того, хто розгортає цей репозиторій для себе (форк або
власна копія) і хоче, щоб GitHub Actions справді надсилав повідомлення в
Telegram кожні 2 години.

## 1. Створіть Telegram-бота

1. Відкрийте [@BotFather](https://t.me/BotFather) в Telegram, надішліть
   `/newbot` і дотримуйтесь інструкцій. У відповідь ви отримаєте токен —
   рядок вигляду `123456789:AAExampleTokenDoNotUseThisOne`. Це і є
   `TELEGRAM_BOT_TOKEN`.
2. Дізнайтесь `chat_id`, куди бот надсилатиме повідомлення:
   - **Особисті повідомлення собі:** напишіть своєму боту будь-яке
     повідомлення (наприклад, "привіт"), а тоді відкрийте в браузері
     `https://api.telegram.org/bot<TOKEN>/getUpdates` (підставте свій
     токен) і знайдіть у відповіді `"chat":{"id": ЧИСЛО, ...}` — це і є
     `chat_id`. Простіше: напишіть [@userinfobot](https://t.me/userinfobot)
     — він одразу покаже ваш `id`.
   - **Канал або група:** додайте бота туди як адміністратора, напишіть
     будь-яке повідомлення в чат і так само перевірте `getUpdates` — для
     каналів `chat_id` зазвичай від'ємний, напр. `-1001234567890`.

## 2. Додайте секрети в репозиторій

У вашому репозиторії на GitHub: **Settings → Secrets and variables →
Actions → New repository secret**, додайте два секрети:

| Назва                | Значення                          |
|-----------------------|-----------------------------------|
| `TELEGRAM_BOT_TOKEN`   | токен від @BotFather               |
| `TELEGRAM_CHAT_ID`     | ваш chat_id або id каналу/групи    |

Обидва workflow (`check-coin-news.yml` і `watchdog.yml`) використовують ці
самі два секрети.

### Кілька ботів і/або чатів одразу

Якщо хочете надсилати повідомлення в кілька чатів і/або через кількох
різних ботів — замість (або на додачу до) `TELEGRAM_BOT_TOKEN`/
`TELEGRAM_CHAT_ID` додайте секрет `TELEGRAM_RECIPIENTS`: список пар
`токен_бота:chat_id`, кожна пара з нового рядка (або через кому):

```
111111111:AAбот-один-токен:123456789
222222222:BBбот-два-токен:-1009876543210
111111111:AAбот-один-токен:-1005555555555
```

(Токен бота сам містить двокрапку — це нормально, парсер розбиває кожен
рядок по **останній** двокрапці, а не по першій.) Якщо `TELEGRAM_RECIPIENTS`
заданий — саме він використовується, а `TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID`
ігноруються. Якщо не заданий — усе працює як раніше, з однією парою.
Повідомлення надсилається кожному отримувачу окремо: якщо один бот/чат
чомусь недоступний (наприклад, бота видалили з каналу), іншим все одно
прийде повідомлення.

## 3. Дозвольте Actions комітити зміни

Основний workflow після кожного запуску, коли з'являються нові новини,
комітить оновлений `state/seen_news.json` назад у репозиторій — так він
"запам'ятовує", що вже було надіслано. Для цього потрібно:

**Settings → Actions → General → Workflow permissions** → оберіть
**"Read and write permissions"** і збережіть.

Без цього кроку workflow працюватиме (перевірятиме сайт і надсилатиме
повідомлення), але не зможе закомітити стан, і при кожному запуску
намагатиметься надіслати ті самі новини повторно.

## 4. Перевірте вручну

Не чекайте 2 години — на вкладці **Actions → Check NBU coin news → Run
workflow** можна запустити перевірку вручну. Перший запуск лише збереже
поточний список новин, статей із sitemap і товарів у каталозі (нічого не
надішле в Telegram) — це очікувано, так задумано, щоб не засипати вас
повідомленнями про 100+ вже наявних новин. Щоб переконатись, що Telegram
працює, можна тимчасово видалити один ID зі
[`state/seen_news.json`](state/seen_news.json),
[`state/seen_sitemap.json`](state/seen_sitemap.json) або
[`state/seen_lots.json`](state/seen_lots.json) і запустити workflow ще
раз — відповідний запис "стане новим" і прийде повідомлення. (Для
`seen_lots.json` це має сенс лише тоді, коли каталог зараз не порожній —
видаляйте ID товару, який справді зараз є на
[сторінці каталогу](https://coins.bank.gov.ua/catalog.html).)

## 5. Раннє попередження через sitemap: що варто знати

Окрім сторінки новин, workflow також перевіряє
[`sitemap.xml`](https://coins.bank.gov.ua/sitemap.xml) і надсилає окреме
повідомлення "З'явилась стаття в sitemap НБУ, очікуємо на публікацію в
новинах на сайті", якщо стаття вже є в sitemap, але ще не потрапила до
списку новин. Це працює через `scripts/check_sitemap.py` і власний файл
стану `state/seen_sitemap.json`, незалежний від `state/seen_news.json`.

Один нюанс, про який варто знати: sitemap статей на сайті містить не лише
новини, а й службові сторінки — правила, FAQ, "План випуску монет" тощо.
Сторінка "План випуску монет" (`plan-vipusku-monet/a-580.html`), наприклад,
має в заголовку слово "монет" і теоретично могла б хибно спрацювати як
"нова монетна стаття". На практиці це не проблема: перший запуск одразу
запам'ятовує ID усіх наявних на момент старту сторінок sitemap (включно з
цією), тож повторно вона вже ніколи не "стане новою" — навіть коли НБУ
згодом редагує цю сторінку (це міняє лише дату зміни, а не ID). Ризик
хибного спрацювання існує лише в теоретичному випадку, якщо НБУ коли-небудь
створить ще одну службову (не новинну) сторінку зі словом "монет" у
заголовку вже після того, як бот почав стежити за сайтом — тоді прийде
одне зайве повідомлення. Це прийнятний компроміс: ідеально відрізнити
"новину" від "довідкової сторінки" по самому sitemap неможливо, бо обидва
типи сторінок мають однаковий формат URL.

## 6. Перевірка каталогу: чим вона відрізняється від двох попередніх

Третя перевірка — `scripts/check_lots.py` — стежить не за новинами, а за
[самим каталогом](https://coins.bank.gov.ua/catalog.html): списком того,
що прямо зараз можна покласти в кошик. Надсилає повідомлення "Новий лот у
продажу на сайті НБУ", коли в каталозі з'являється товар, якого не було
на попередньому запуску. Стан — у
[`state/seen_lots.json`](state/seen_lots.json).

Два нюанси, якими ця перевірка відрізняється від новин і sitemap:

- **Фільтр `KEYWORDS` тут не діє.** Назви товарів у магазині зазвичай не
  містять слова "монета" взагалі (товар називається просто за темою,
  напр. `"Архістратиг Михаїл" (з)`), тому текстовий фільтр за ключовими
  словами лише сховав би реальні лоти. Каталог і так показує тільки те,
  що можна купити прямо зараз, — додатковий фільтр тут не потрібен.
- **Файл стану не накопичує ID назавжди, а зберігає "знімок" каталогу на
  момент останнього запуску.** Якщо товар розкупили (зник із каталогу), а
  потім він з'явився знову (наприклад, повернули частину тиражу) — це
  знову вважається "новим лотом" і прийде повідомлення. Це свідоме
  рішення: повторна поява в продажу — це саме той момент, який не хочеться
  пропустити, так само як і перша поява.

## 7. Коли сайт блокує запити жорсткіше

Захист сайту (Bunny Shield) іноді блокує запити з хмарних IP-адрес — а
саме такі й у GitHub Actions — навіть із правильним User-Agent і сесією:
буває звичайний "403 Forbidden", буває JavaScript-челендж, який здатен
пройти лише справжній браузер. У такому разі `http_client.SiteClient`
сам, автоматично, у межах того самого запуску:

1. Шукає робочий безкоштовний публічний проксі (перевіряє одразу десятки
   кандидатів із кількох відкритих списків, бо переважна більшість мертва
   або заблокована так само) і, якщо знаходить — продовжує через нього.
   Проксі, geolocated в росію, виключаються завжди, незалежно від
   джерела списку.
2. Якщо проксі не знайшлось і це саме JS-челендж (не звичайний блок) —
   піднімає headless Chromium (Playwright) прямо в workflow, проходить
   виклик як звичайний браузер, і далі використовує отримані ним cookie
   для решти запитів у цьому запуску.

Жодних додаткових секретів чи налаштувань для цього не треба — усе
працює "з коробки" в тому самому workflow. Єдиний наслідок, який ви
можете помітити: коли спрацьовує цей резервний механізм, один запуск
може тривати не секунди, а хвилину-дві (пошук проксі та/або запуск
браузера займають час). Якщо жоден зі способів не допоміг — крок
завершується помилкою як зазвичай, і про це прийде сповіщення (див.
watchdog нижче).

## 8. Watchdog: що робити, якщо сповіщення раптом припинились

Окремий workflow [`watchdog.yml`](.github/workflows/watchdog.yml) раз на 3
години перевіряє:

- чи основний workflow взагалі колись запускався;
- чи він не в стані "вимкнено" (`state != active`);
- чи останній *запланований* (не ручний) запуск був не пізніше, ніж 6
  годин тому (це в 3 рази більше за звичайний інтервал у 2 години — щоб
  не спрацьовувати помилково через випадкові затримки в розкладі GitHub);
- чи за останню добу набралось хоча б 4 запланованих запуски з
  очікуваних ~12 (раз на 2 години) — цей окремий поріг ловить ситуацію,
  коли розклад технічно "працює", але GitHub мовчки пропускає більшість
  запусків, а не лише один-два поспіль. Саме так і сталось на практиці:
  розклад одного разу не спрацював жодного разу за понад 3 години, хоча
  мав би запуститись 15+ разів — окремі ручні запуски це маскували, поки
  не з'явилась ця перевірка "за добу".

Якщо щось із цього не так — прийде повідомлення в Telegram із поясненням.
Окремо основний workflow сам одразу сповіщає в Telegram, якщо якийсь із
його кроків впав з помилкою (`if: failure()` крок у кінці
`check-coin-news.yml`).

**Важливе обмеження, яке варто знати:** GitHub автоматично вимикає
`schedule`-workflow, якщо в репозиторії 60 днів не було жодної активності
(комітів). Це стосувалось би й самого watchdog'а — якщо репозиторій зовсім
"замре" на два місяці (наприклад, довго немає жодної нової монети чи
оновлення в sitemap, тож нема чого комітити), обидва workflow могли б
вимкнутись одночасно, і сповістити про це вже нікому.

Для цього є третій workflow — [`heartbeat.yml`](.github/workflows/heartbeat.yml).
Раз на місяць (1-го числа) він робить один тривіальний комміт
(оновлює позначку часу в [`state/heartbeat.json`](state/heartbeat.json)),
просто щоб у репозиторії завжди була хоч якась активність у межах
60-денного вікна. Жодних сповіщень він не надсилає — це суто "утримувач
життя" для розкладів. Завдяки йому основний workflow і watchdog більше не
вимкнуться самі, навіть якщо новин не буде місяцями.

## 9. Захист репозиторію від стороннього втручання

Якщо репозиторій публічний, будь-хто може відкрити Pull Request. Ось що
варто налаштувати, щоб чужий PR не міг ані вкрасти секрети, ані непомітно
зламати автоматизацію:

1. **Найважливіше — схвалення запуску Actions для чужих PR.**
   **Settings → Actions → General → "Fork pull request workflows in this
   repository"** → оберіть **"Require approval for all outside
   collaborators"**. Без цього чужий Pull Request (навіть із заміненим
   workflow-файлом, що намагається переслати секрети собі) міг би сам
   запустити Action. З цим налаштуванням жоден workflow не запуститься на
   чужому PR, доки ви вручну не натиснете "Approve and run" на вкладці
   Actions.
2. **Не додавайте стороннім людям право Write (Collaborators and
   teams).** Будь-хто з правом запису може напряму редагувати
   `.github/workflows/*.yml` — а отже, і дописати крок, який просто
   виведе секрети в лог або відправить їх кудись. Тримайте
   **Settings → Collaborators and teams** порожнім (лише ви) або
   додавайте туди тільки тих, кому довіряєте як собі.
3. **"Allow GitHub Actions to create and approve pull requests"**
   (**Settings → Actions → General → Workflow permissions**) — залиште
   вимкненим (за замовчуванням і так вимкнено). Нашим workflow це не
   потрібно, а увімкнене — зайва можливість для зловживання.
4. **Не вмикайте branch protection "Require a pull request before
   merging" на `main`** у строгому вигляді. Це виглядає як "захист", але
   заблокує й прямі коміти самого бота (`state/*.json`, heartbeat) — вони
   теж підпорядковуються правилам захисту гілки, як і людина. Якщо
   хочеться додатково захистити `main` від випадкових прямих пушів людей
   (не бота), для цього є новіший механізм **Rulesets**
   (**Settings → Rules → Rulesets**) з винятком (bypass) для GitHub
   Actions — але для одноосібного проєкту це зазвичай не потрібно.
5. Секрети (`TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, `TELEGRAM_RECIPIENTS`)
   ніколи не з'являються в логах у відкритому вигляді — GitHub автоматично
   маскує будь-яке значення секрету, яке трапляється у виводі логів, навіть
   якщо воно підставлене напряму в команду (як у `curl` в кроці
   `Notify on failure`).
6. Публічні репозиторії на GitHub автоматично мають увімкнені **secret
   scanning** і **push protection** (GitHub сам попередить, якщо у коміті
   випадково опиниться щось схоже на реальний токен) — додатково нічого
   вмикати не треба.

Підсумок для одноосібного проєкту (найпоширеніший випадок): пункти 1–3 —
зробити обов'язково, пункт 4 — свідомо пропустити (не заважати боту),
пункти 5–6 — вже увімкнені за замовчуванням, нічого робити не треба.

## 10. Щоб репозиторій знаходили в пошуку (необов'язково)

Якщо хочете, щоб проєкт бачили інші люди, найбільше дають дві речі, які
налаштовуються **не у файлах, а в самому GitHub** (файли README вже
підготовлені):

1. **Опис (About).** Головна сторінка репозиторію → шестерня біля "About"
   справа → поле **Description**. Напишіть один рядок із ключовими
   словами, напр.: *"Сповіщення в Telegram про нові пам'ятні та
   інвестиційні монети НБУ. Безкоштовно на GitHub Actions."* Саме цей
   текст Google найчастіше показує як опис у видачі.
2. **Topics (теги).** Там само, поле **Topics**. Вони індексуються і
   GitHub-пошуком, і Google. Розумний набір:

   ```
   ukraine, coins, numismatics, nbu, telegram-bot, telegram-notifications,
   github-actions, web-scraping, monitoring, price-tracker, python,
   монети, нумізматика
   ```

   (Topics мають бути малими літерами, слова через дефіс; кирилиця
   дозволена, але латинські теги дають більше охоплення.)

3. Там само варто поставити галочку **"Use your GitHub Pages website"**
   → ні, а от **Include in the GitHub Archive Program** можна лишити як є.

Ще дрібниці, які допомагають: не робіть репозиторій приватним (приватні
не індексуються взагалі), і додайте файл ліцензії (**Add file → Create
new file → `LICENSE`** → GitHub запропонує шаблони, напр. MIT) — репозиторії
з ліцензією виглядають надійніше і частіше потрапляють у добірки.

## Налаштування фільтра ключових слів

За замовчуванням бот реагує на заголовки, що містять "монет". Стосується
це лише перевірки новин і sitemap — перевірка каталогу (`check_lots.py`)
цей фільтр не використовує в принципі (чому — див.
["6. Перевірка каталогу"](#6-перевірка-каталогу-чим-вона-відрізняється-від-двох-попередніх)
вище), тож для неї нічого налаштовувати не треба.

Щоб змінити або розширити список для новин і sitemap (наприклад, додати
банкноти), додайте змінну середовища `KEYWORDS` **в обидва** відповідні
кроки файлу `.github/workflows/check-coin-news.yml` — і
`Check for new coin news`, і `Check sitemap for early coin articles` —
щоб фільтр був однаковим для обох:

```yaml
      - name: Check for new coin news
        env:
          TELEGRAM_BOT_TOKEN: ${{ secrets.TELEGRAM_BOT_TOKEN }}
          TELEGRAM_CHAT_ID: ${{ secrets.TELEGRAM_CHAT_ID }}
          TELEGRAM_RECIPIENTS: ${{ secrets.TELEGRAM_RECIPIENTS }}
          KEYWORDS: "монет,банкнот"
        run: python scripts/check_news.py

      - name: Check sitemap for early coin articles
        env:
          TELEGRAM_BOT_TOKEN: ${{ secrets.TELEGRAM_BOT_TOKEN }}
          TELEGRAM_CHAT_ID: ${{ secrets.TELEGRAM_CHAT_ID }}
          TELEGRAM_RECIPIENTS: ${{ secrets.TELEGRAM_RECIPIENTS }}
          KEYWORDS: "монет,банкнот"
        run: python scripts/check_sitemap.py
```
